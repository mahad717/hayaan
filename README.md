# Mercado — Next.js + Supabase + Cloudflare starter

A production-ready e-commerce starter built with **Next.js 16 (App Router)**,
**Prisma**, **Tailwind CSS 4 + shadcn/ui**, **Supabase-ready auth & data layer**,
and **Cloudflare Pages** deployment config.

## What's inside

- 🛍️ Catalog grid with search, category filters, and sorting
- 📦 Product detail page with image gallery and quantity picker
- 🛒 Persistent cart drawer with live totals
- 🔐 Email + password auth (bcrypt locally / Supabase Auth in production)
- 💳 Multi-step checkout with shipping + payment options
- 👤 Order history view
- 🛠️ Admin dashboard with full product CRUD
- 🎨 Tailwind 4 + shadcn/ui (New York style)
- 🚀 One-command seed for demo products
- ☁️ `wrangler.toml` for Cloudflare Pages deployment

## Quick start (local demo)

```bash
# 1. Install dependencies
bun install

# 2. Push the Prisma schema to local SQLite
bun run db:push

# 3. Start the dev server (auto-runs in this sandbox)
bun run dev

# 4. Seed the demo catalog + admin user
curl -X POST http://localhost:3000/api/seed
# → Admin: admin@shop.demo / admin123

# 5. Open http://localhost:3000 (or the preview panel in this sandbox)
```

## Switching from local Prisma to real Supabase

Every API route already has a Supabase code path that activates when these env
vars are present:

```bash
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi...
```

## Deploy to Cloudflare Workers (Workers Builds)

This project deploys as a **Cloudflare Worker** using [`@cloudflare/next-on-pages`](https://github.com/cloudflare/next-on-pages) to translate the Next.js build into a Workers-compatible bundle. Workers Builds is Cloudflare's newer CI/CD pipeline (replacing the legacy Pages auto-deploy) — it requires both a build command AND a deploy command.

### Why Workers (not Pages)?

Cloudflare Workers can serve both static assets AND dynamic API routes from a single deploy. The `wrangler.toml` in this repo points `main = ".vercel/output/static/_worker.js/index.js"` at the Worker entry generated by `@cloudflare/next-on-pages`, and `[assets]` at the same directory for static file serving. `wrangler deploy` uploads both in one shot.

### Dashboard settings (Workers Builds)

In your Cloudflare dashboard → **Workers & Pages → hayaan → Settings → Builds & deployments**, set:

| Field | Value |
|---|---|
| **Build command** | `bun run build:pages` |
| **Deploy command** | `npx wrangler deploy` |
| **Root directory** | `/` |
| **Compatibility flags** | `nodejs_compat` (already set in `wrangler.toml`) |

### Environment variables

Under **Settings → Variables and Secrets**, add:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://mqyhgyakhfhuctnvezby.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | your anon key (public — safe for browser) |
| `SUPABASE_SERVICE_ROLE_KEY` | your service_role secret (server-only — never expose) |

### How it works

When you push to `main`:

1. **Workers Builds** clones your repo and runs `bun install`
2. **Build command** (`bun run build:pages`) runs `@cloudflare/next-on-pages`:
   - Runs `next build` internally to produce the standard Next.js output
   - Translates each API route + page into an Edge Function (required by the adapter — that's why every `route.ts` has `export const runtime = "edge";`)
   - Emits a Worker entry at `.vercel/output/static/_worker.js/index.js`
   - Writes `.assetsignore` so wrangler doesn't re-upload `_worker.js/` as a static asset
3. **Deploy command** (`npx wrangler deploy`) reads `wrangler.toml`:
   - Uploads `_worker.js/index.js` as the Worker script (32 KB)
   - Uploads the static assets directory (64 files — HTML, CSS, JS chunks, images)
   - Binds the Worker to the ASSETS binding for static file serving
4. Your Worker is live at `https://hayaan-market.<your-subdomain>.workers.dev`

### CLI deploy alternative

```bash
# Build locally
bun run build:pages

# Deploy (requires wrangler CLI + Cloudflare auth)
npx wrangler deploy

# Or dry-run to verify config without deploying
npx wrangler deploy --dry-run
```

### Why lazy Prisma + bcrypt?

`@prisma/client` and `bcryptjs` use Node.js built-ins (`fs`, `crypto`) that don't exist on the Workers runtime. To keep them out of the Cloudflare bundle, they're loaded via dynamic `await import()` inside the local-dev fallback branches. In production, `isSupabaseServerEnabled` is always `true`, so those branches never execute and the bundler tree-shakes the Node-only modules out.

If you ever want to remove the local Prisma fallback entirely, delete `src/lib/db.ts`, `src/lib/auth-session.ts`, `src/app/api/seed/route.ts`, and the `if (!isSupabaseServerEnabled)` branches in every route.
